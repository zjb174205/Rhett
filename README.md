## 2. 第一阶段目标：完成需求验证，而不是抢先开发

1. **需求归档**：为两个候选项目分别写清目标人群、使用场景、核心痛点及不做什么。
2. **轻量调研**：访谈潜在用户，记录真实问题、当前替代方案与竞品，不以主观喜好代替证据。
3. **原型验证**：各制作一份最小流程图或低保真原型，识别主流程和运营/审核成本。
4. **评估对比**：按需求强度、获客难度、开发复杂度、合规与内容审核成本、可持续性比较。
5. **形成决策记录**：明确继续验证、暂缓或选择某个 MVP 的依据；在证据不足前不承诺具体上线时间。

**阶段交付物**：两份候选方向简述、基础验证记录、一份对比决策记录、可演示的低保真原型（如适用）。

## 3. 待确认问题

- **用户与场景**：首批目标用户是谁？优先选择一所学校、多个学校，还是若干城市地标？
- **价值与指标**：用户为什么回来？用什么指标判断需求成立（例如有效访谈、任务完成率、回访意愿）？
- **功能边界**：两个方向各自的最小闭环是什么？哪些社交或内容功能必须推迟？
- **资源与平台**：可投入的时间、预算、开发能力和首发平台分别是什么？
- **风险与运营**：用户隐私、UGC 审核、位置数据及地图使用、内容版权和维护责任如何处理？
- **业务关系**：接单业务是否仅作为独立现金流和作品集，不与产品账户、数据或代码混用？

以上均为待决策事项，**不得把提问误写成已确认的产品需求**。

## 5. 维护约定

- 各候选方向分别维护，避免把不同项目的需求、原型与代码混在一起。
- 事实、假设、待验证问题和已确认决策分开写；每项重要决定记录日期与理由。
- 不上传客户隐私、合同中的敏感信息、账号密钥或未经授权的交付文件。
- 每次有实际进展时更新本页“状态”和对应方向文档；除非有新证据，不改变最终产品方向的未定状态。

**下一步**：为两个方向各列出 3 个可观察的真实用户问题，并各访谈至少 5 位相关潜在用户；数量仅作起步建议，不是统计意义上的验证阈值。
